1. Executive Summary

WorkforceIQ is a staff management platform for multi-outlet operations. It covers scheduling, attendance, leave, allocation, staff documents, outlet capacity planning, and demand forecasting. The system is built as a monorepo with separate web, API, and ML components, and is designed specifically for restaurant operations.

It supports employee directory management, outlet and department structures, staffing ratios, roster publishing, approvals, role-based permissions, notifications, and operational dashboards. The project includes a documented implementation roadmap, multiple migration phases, and a clear set of feature milestones and work reports.

2. Problem It Solves

The project addresses common workforce and operational problems in hospitality businesses including:

  • Manual and inconsistent scheduling across multiple outlets
  • Incomplete visibility into staffing requirements vs. actual deployment
  • Difficulty monitoring attendance, leave, and approvals
  • Need for role-based access across employee, chef, HR, admin, and supervisory roles
  • Limited forecasting and capacity planning for demand-driven staffing
  • Compliance and document management for employee records
  • Need for in-app, email, and WhatsApp notification orchestration

4. Core Architecture

Application Layers

  • Web: Next.js 14 + React 18 + Tailwind + TanStack Query + Zustand
  • API: NestJS TypeScript + PostgreSQL + Redis + Bull
  • ML Service: Python FastAPI for forecasting and staffing insights
  • Shared: Reusable types and constants in packages/shared

Operational Model

  • Database hosted on Supabase Postgres 16
  • Redis used for queue processing and notifications
  • Manual migration workflow with numbered SQL files
  • Role and outlet scoping enforced at server side

10. Security and Compliance Notes

  • JWT + refresh-token rotation is implemented for secure authentication
  • Rate limiting is configured for login and global API traffic
  • Server-side outlet scoping prevents cross-outlet unauthorized access
  • Role-based permission enforcement is part of the request flow
  • Aadhaar is designed to be masked to the last four digits and stored carefully
  • Document encryption and access logging are part of the advanced document module
  • Credential hygiene and secret rotation are highlighted as operational best practices
Security and credentials are intentionally tracked in documentation, but raw secrets are not committed to the repository.

11. System Workflows

Scheduling Workflow

  • Generate or maintain weekly shift templates
  • Apply outlet and staff-specific restrictions
  • Allow manager adjustments and manual shift edits
  • Publish roster to employees and notify relevant stakeholders

Attendance Workflow

  • Clock-in and clock-out records are captured
  • Kiosk devices can be enrolled for front-of-house and staff access
  • Source tracking distinguishes standard vs. kiosk attendance methods

Leave Workflow

  • Employees submit leave requests
  • Managers review and approve or reject
  • Notifications are triggered to the relevant parties

Notification Workflow

  • Events are emitted from business actions
  • Recipients are resolved by role, outlet scope, and preferences
  • Messages are delivered through in-app, email, or WhatsApp if enabled

12. Database and Migration Strategy

The project uses a database-first approach with numbered migration files under the assets/db folder.

  • Schema evolution is handled by incremental numbered SQL files
  • Each migration may have a matching rollback file
  • DB migrations are manually applied and not fully wired into a generic runner at the repo root
  • Supabase Postgres is used for the hosted environment, with session pooler configuration

13. Deployment Architecture

Production is configured for Render with a render.yaml deployment blueprint. The setup involves:

  • PostgreSQL service
  • Redis service
  • API deployment
  • Web frontend deployment
  • Environment configuration using .env values

14. Development Setup

Project instructions emphasize Windows-first local development and Node 20 compatibility.

  • Node.js 20 required (not 23/24) due to Next.js 14 dev constraints
  • pnpm >= 9 required
  • PostgreSQL 16 required
  • Redis required for Bull queues
  • Commands include: pnpm install, pnpm dev, pnpm build, pnpm lint, pnpm test, pnpm typecheck

15. Default Login and Environment Notes

The documentation indicates a default admin login pattern, but credentials are treated as operational secrets and are never committed to git.

  • Primary admin identity: admin@workforceiq.app
  • HR admin examples are present in project docs for operational setup
  • Environment variables include DB, Redis, JWT, refresh, email, and document security settings

18. Business Value Summary

WorkforceIQ is positioned as a practical software system for restaurant groups that want a single source of truth for workforce management. It reduces the gap between staffing needs and actual deployment while enabling deeper operational oversight, staff self-service, and managerial decision support. The project combines staffing operations, compliance, forecasting, and notifications into a consolidated system.

19. Final Summary

This project is a large, production-oriented workforce management system built for restaurant operations. It includes a web app, API, ML service, SQL migrations, deployment configuration, and a detailed architecture report. The codebase is designed for multi-outlet staffing management, operational visibility, and data-driven decision making across HR, management, and employee workflows.
